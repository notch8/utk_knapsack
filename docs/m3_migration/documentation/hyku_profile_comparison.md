# Migrated profile vs Hyku's default m3 profile

Follow-up notes, not a task list. Generated by `compare_to_hyku.rb`:

```bash
ruby docs/m3_migration/scripts/compare_to_hyku.rb
```

It compares the keys that change behavior (`range`, `data_type`, `indexing`,
`form`, `view`, `property_uri`, `cardinality`, `requirement`) for every property
Hyku declares, and ignores prose and provenance keys that are expected to differ.

Of Hyku's 80 properties: **3 identical, 17 differing, 60 absent.**

## Schema validity

The migrated profile produces **zero JSON-schema errors**, and every property
key it emits is either enumerated in the schema or used identically by Hyku's
own profile. Worth recording, because three of our keys are *not* in the
schema's enumerated list:

| Key | Schema enumerates | Notes |
|---|---|---|
| `controlled_values` | `controlled_value` (singular) | Hyku uses the plural too. |
| `mappings` | `mapping` (singular) | Hyku uses the plural too. |
| `sample_values` | `sample_value` (singular) | Hyku uses the plural too. |
| `form`, `view` | *(not enumerated)* | Read by Hyrax code; Hyku uses both. |

The `properties.*` subschema does not set `additionalProperties: false`, so
neither spelling errors. The singular names in the schema appear to be the ones
out of step with practice, and both profiles use the plurals.

## 1. Missing `view.render_as` — the one real gap

Hyku gives 11 properties a render behavior the conversion drops, because
Allinson Flex has no `render_as` concept for the converter to carry over. Ours
come out as bare `{html_dl: true}`, so these values render as plain text.

| Property | Hyku `render_as` | What we lose |
|---|---|---|
| `creator` | `linked` | Clickable facet link |
| `contributor` | `linked` | Clickable facet link |
| `keyword` | `linked` | Clickable facet link |
| `language` | `linked` | Clickable facet link |
| `publisher` | `linked` | Clickable facet link |
| `resource_type` | `linked` | Clickable facet link |
| `subject` | `linked` | Clickable facet link |
| `date_created` | `linked` (plus `search_field: date_created_tesim`) | Clickable facet link |
| `license` | `external_link` | Followable URL |
| `rights_statement` | `rights_statement` | Rights badge rendering |

This is the only difference that reads as a defect rather than a deliberate
divergence. Adding a `RENDER_AS` map to the conversion would close it.

## 2. `form: {display: true}` vs `{primary: false}` — cosmetic

Hyku writes `{primary: false}` on its below-the-fold fields; we write
`{display: true}`. Both land the field in `secondary_terms`, which selects on
`definition[:display] && !definition[:primary]`. Hyku relies on the `display:
true` default applied at registration; we set it explicitly. Same outcome, and
ours is the more literal of the two.

## 3. `requirement:` retained — inert

We carry the source's `requirement: optional|required` through; Hyku omits the
key entirely. Hyrax derives requiredness from `cardinality.minimum` and
`form.required`, not from this key, so it is documentation rather than behavior.

## 4. Ranges: resolved, no longer a difference

This section previously recorded eight properties ranged `anyURI` in ours where
Hyku has `string`, and treated the divergence as a deliberate reflection of
UTK's controlled-vocabulary model.

That reading was wrong. `anyURI` makes Hyrax coerce the value to an `RDF::URI`,
whose `as_json` is `{"@id" => "..."}`, which Solr rejects as a malformed atomic
update. Saving a work with any such field populated 500s. All 77 `anyURI` ranges
are now `xsd:string`, matching Hyku, and the controlled vocabularies are
untouched — `range` drives coercion, `controlled_values` names the authority.

`date_created` remains a real difference: `dateTime` in Hyku, `string` in ours,
carried from the source and defensible given UTK's EDTF-style date values.

## 6. Class scoping: descriptive fields not on the FileSet

Comparing `available_on` lists directly is meaningless here, since the two
profiles declare entirely different classes. What is comparable is the *shape*:
whether a property is scoped to the file set, the work types, or both. Ten
properties differ.

Nine are the same case, all descriptive fields:

| Property | Hyku | Ours |
|---|---|---|
| `abstract`, `contributor`, `date_created`, `keyword`, `language`, `license`, `publisher`, `resource_type`, `subject` | file set + work types | work types only |

Hyku makes these available on `Hyrax::FileSet` as well, so an individual file
can carry its own subject, language, and so on. UTK's source profile never
scoped descriptive metadata to file sets, and the conversion preserves that.
Whether UTK wants per-file descriptive metadata is a modeling question for the
metadata owners, not a conversion defect.

`label` is the inverse and is deliberate:

| Property | Hyku | Ours |
|---|---|---|
| `label` | file set + work types | file set only |

It holds a download filename, and `validate_label_prop` only requires that
`available_on` *include* the file set model. See the note in
[`form_excluded_properties.md`](form_excluded_properties.md).

## 7. Smaller differences

- **`facetable` dropped** from `contributor`, `keyword`, `publisher`. The source
  did not mark them facetable, so the conversion did not add it. If UTK wants
  these facetable, the source profile is where to say so.
- **`rights_statement` loses `cardinality.maximum: 1`**, removed by the
  contradiction-resolution rule (the source declared `multi_value: true`
  alongside `maximum: 1`).
- **`label` gains `view: {html_dl: true}`** where Hyku has none.
- **`title` and `rights_statement`** carry `requirement: required` where Hyku
  has no such key; the effective requiredness matches via `cardinality`.

  `show_pdf_download_button`, `media_viewer`, `video_embed`,
  `hide_from_catalog_search`, `split_from_pdf_id`, `is_child`
- **Versioning and internals** — `alternate_version_id`, `newer_version_id`,
  `previous_version_id`, `related_item_id`, `bulkrax_identifier`,
  `arkivo_checksum`, `import_url`, `relative_path`
- **Accessibility** — `accessibility_feature`, `accessibility_hazard`,
  `accessibility_summary`, `alt_text`
- **Compound structures** — `redirects`, `relationships`, `relationship_item`,
  `relationship_type`, `identifiers`, `identifier_value`, `identifier_type`,
  `participants`, `participant_name`, `participant_role`, `transcript_ids`,
  `shared_title`
- **Generic descriptive fields UTK models differently** — `description`
  (UTK uses `abstract`), `identifier` (UTK uses `primary_identifier`,
