Hyrax 5.3+ · Flexible Metadata

Allinson Flex to M3

The two formats share a skeleton and a version string. That is precisely why a profile can read correctly, parse cleanly, and still fail validation hundreds of times.

Hyrax v5.3 replaced the Allinson Flex gem with built-in flexible metadata (HYRAX_FLEXIBLE=true). Profiles live in the hyrax_flexible_schemas table and are validated by Hyrax::FlexibleSchemaValidatorService.

Both formats declare m3_version: 1.0.beta2 and share the same top-level blocks — profile, classes, contexts, mappings, properties. The substantive difference sits in one key. Allinson Flex used indexing: for behavioral hints. Hyrax M3 uses it for literal Solr field names. A profile whose indexing: says displayable is declaring a Solr field that does not exist.

Those numbers come from converting a real profile: UTK Digital Collections v54, 191 properties across 9 classes. Every error traced to a single key. Only two properties validated as written. The converted profile is 195 properties across 10 classes.

But displayable was only the loud failure. The quiet ones pass every validator: a range with no Valkyrie type raises when a work type builds its attributes, and a literal display_label is valid but never localizes. Counting errors measures the first kind and not the second.

Strict blocks and loose blocks

A frequent misreading: the properties.* subschema lists allowed keys but does not set additionalProperties: false. Extra keys are legal, and Hyrax reads several of them. Do not strip controlled_values, mappings, or sample_values to "conform".

The profile: block is strict. Only date_modified, responsibility, responsibility_statement, type, and version are permitted.

Decision points

Eight calls that a mechanical conversion cannot make for you. They are numbered because later ones depend on earlier ones.

01Class naming: Valkyrie or ActiveFedora

ClassValidator requires every class to be a registered curation concern, compared against Valkyrie.config.resource_class_resolver. A mismatch reads:

Mismatched Valkyrie classes found: 'Image' should be 'ImageResource'.

Flexible metadata is Valkyrie-only. An ActiveFedora app cannot load a flexible profile no matter how the profile is written. Keeping ActiveFedora names yields a structurally valid profile that will not load until models migrate; using ...Resource names yields one that loads on a migrated app and misleads before then. Either way the model migration is a prerequisite, not a follow-up.

02Renaming and removing classes

A source profile's work types rarely match the ones the application registers. Two declarative maps drive this, and both apply to classes and to every available_on.class list — the half that is easy to miss by hand. For UTK: Image becomes StillImage, while Attachment and GenericWork are dropped.

A rename also updates the class's own display_label when the label merely echoed the old name, or the UI keeps showing "Image" under the key StillImage.

Dropping a class can orphan properties

A property scoped only to a dropped class ends up with an empty available_on.class — a silently broken property, not a validation error. Check exclusive scopes before dropping, and let the conversion fail loudly rather than write the orphan.

03Required classes

Every profile must declare admin_set_model, collection_model, and file_set_model — in Hyku, AdminSetResource, CollectionResource, and Hyrax::FileSet. Allinson Flex profiles usually declare only work types, so all three are typically missing. This cascades: core properties must be available on every class, so adding three classes edits available_on on every core property.

04FileSet-level metadata

Hyrax expects file-level technical metadata — checksums, dimensions, format — on the FileSet, and requires a label property available on file_set_model. Allinson Flex profiles often model this as a work type instead.

Not a mechanical edit

Re-scoping properties to Hyrax::FileSet is a data-model change. Existing records hold that metadata at the work level and need migration. Confirm with the metadata owners before shipping.

05Core metadata conformance

CoreMetadataValidator enforces title, date_modified, date_uploaded, depositor, and creator — the last injected even when absent from the YAML. Each must exist, cover every class, and match the exact predicate and index keys in core_metadata.yaml.

creator is the usual conflict. Hyrax demands http://purl.org/dc/elements/1.1/creator, while many profiles use a MARC relator such as .../relators/cre. Satisfying the validator changes an existing predicate, affecting indexing, OAI-PMH output, and downstream consumers. If the relator must survive, keep it under a separate key and let creator take the DC predicate. This is a metadata-governance decision, not a technical one.

06Multiplicity contradictions

Profiles commonly declare multi_value: true alongside cardinality.maximum: 1. Hyrax checks data_type, then multi_value, then cardinality — so the field is multi-valued and the maximum: 1 is inert. In the UTK profile, 38 properties carried this contradiction.

Normalize onto data_type and drop the contradicted maximum. Preserving current behavior means array, but some fields are semantically single-valued — an EXIF resolution, a checksum — and were multi-valued only by accident. Surface the list for review rather than silently freezing it.

07Show-page visibility

Most easily missed regression

Show-page rendering is opt-in. A property renders only when it declares a meaningful view: block such as view: {html_dl: true}. Allinson Flex profiles have none — so a mechanical conversion produces a profile where every field disappears from show pages while still validating and indexing correctly.

Restricted fields (admin_only / editor_only) are excluded from the attribute table anyway and need no view: block.

08YAML aliases

If the profile is generated programmatically, Ruby's YAML emitter writes anchors and aliases (&1 / *1) whenever one object is reachable from several places — a shared available_on.class array, for instance. Hyrax loads profiles with YAML.safe_load_file, which rejects aliases:

Psych::BadAlias: Unknown alias: 1

Round-trip through JSON before dumping, so every value is written literally. Hand-edited profiles are unaffected.

Indexing rules

Each indexing: entry must match this pattern, or be one of facetable, admin_only, editor_only, stored_searchable:

^[a-z_]+_(tesi|tesim|teim|ssi|sim|ssm|bsi|isi|dts|dtsi|ti|si|ss|is|bs|dt|ssim)$

displayable satisfies neither, which is why each occurrence produces two errors — one pattern, one enum. Hence 189 properties yielding 378 errors.

  • <name>_tesim — stored, searchable, multi-valued text. Effectively always.
  • <name>_sim — string form for faceting and display.
  • facetable — adds the field to facets.
  • admin_only / editor_only — restrict visibility; also removes the field from the catalog entirely.

Procedure

Convert with a script, not by hand. At ~200 properties manual editing is unreliable; a script is auditable and rerunnable for the next version. convert_allinson_to_m3.rb never writes to its input:

ruby docs/m3_migration/scripts/convert_allinson_to_m3.rb

It reports what it changed. Read that summary — several transforms are judgment calls made on your behalf. What it applies:

  1. Detab the source if tab-indented, in memory only.
  2. Rewrite indexing: — drop displayable, generate real keys, retain enum flags.
  3. Normalize multiplicity onto data_type; drop contradicted maximums.
  4. Add required classes, drop and rename per decisions 01–03.
  5. Add missing core metadata and conform title, creator, keyword.
  6. Add view: blocks so fields still render.
  7. Fix the profile: block — allowed keys only; quote date_modified.
  8. Normalize unmappable range values, keeping controlled_values.format in step.
  9. Apply Blacklight display_label keys where one resolves.
  10. Add form: blocks so properties reach the deposit form, minus the ones flagged autopopulated.
  11. Order the keys within each property: name first, then alphabetical.
The quiet one

A property with no form: block never reaches a metadata form. form_definitions_for skips properties whose form options are empty, so the field is never registered and the display: true default never applies — primary_terms and secondary_terms both miss it. Everything validates; the deposit form is just empty. Hyku's own profile gives 70 of 80 properties a form block, and the 10 without are all system-managed.

Then verify, in order:

  1. Validate against the JSON schema. This is the objective gate.
  2. Validate in a booted app. Schema-clean is necessary but not sufficient.
  3. Review the semantic diff — no property dropped, no key lost, every predicate change intended.

The schema gate, runnable without booting Rails:

cd /path/to/hyrax && ruby -ryaml -rjson_schemer -e '
schemer = JSONSchemer.schema(
  Pathname.new("config/metadata_profiles/m3_json_schema.json"))
errs = schemer.validate(YAML.safe_load_file("m3_profile.yaml")).to_a
puts errs.empty? ? "VALID" : "#{errs.size} errors"
errs.first(20).each { |e|
  puts "  #{e["data_pointer"]}: #{e["data"].inspect} (#{e["type"]})" }'

Then the validators that need Rails:

bundle exec rails r 'p Hyrax::FlexibleSchema.new(
  profile: YAML.safe_load_file("m3_profile.yaml")
).tap(&:valid?).errors.full_messages'

What validation cannot tell you

A profile can pass every validator and still be wrong.

  • Missing view: blocks — fields validate and index, then vanish from show pages.
  • Predicate changes — retargeting creator is structurally fine and semantically significant.
  • Class re-scoping — validates instantly, may strand existing records.
  • Accidental multiplicity — data_type: array on a checksum is legal and wrong.
  • Unmappable range values — rdf-schema#Literal 500s the deposit form; #anyURI renders fine and 500s on save, with an error naming Solr rather than the profile.
  • Unresolved display_label keys — an i18n key with no translation renders as its own raw text.
  • Missing form: blocks — the profile validates, the schema seeds, the work type instantiates, and the deposit form comes up nearly empty. The one that silently loses most of a converted profile.

The last two share a shape: both validators check the profile's structure, and neither resolves a value against the running application. A profile is verified when a work type instantiates and its form builds, not when it saves.

The through-line

Treat validation as a floor, not a finish line. The errors tell you the profile will load. Only a semantic diff tells you it still means what it used to.
